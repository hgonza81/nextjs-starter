# 0013. Observability: OpenTelemetry NodeSDK, logger, local collector

Status: Accepted
Date: 2026-11-13
Epic: 002-platform-hardening

## Context
Until now the only observability is one `console.error` call site (convention C8). Later epics need traces, structured logs and a way to correlate them, without making the app depend on a telemetry backend, without blocking requests, and without leaking personal data. The app has no edge runtime code. Next.js 16.4.6 supports `instrumentation.ts` with `register()` and `onRequestError`.

## Options considered
1. SDK: (a) manual `@opentelemetry/sdk-node` with OTLP/HTTP exporters; (b) `@vercel/otel` (shorter, couples to Vercel conventions, still needs peer packages); (c) no telemetry, logs only.
2. Exporter: OTLP/HTTP (chosen) versus OTLP/gRPC (native and size cost, poor fit for serverless).
3. Logger: (a) own ~40-line module; (b) pino or winston (dependency, transports we do not need); (c) bare `console`.
4. Local collector: (a) Grafana LGTM in one container (`grafana/otel-lgtm`); (b) Jaeger (traces only); (c) none.

## Decision
- **SDK:** manual `@opentelemetry/sdk-node` with OTLP/HTTP trace, log and metric exporters (selected by the SDK from `OTEL_*`, not pinned in code: see "Implementation notes" and "Review of step 2"), started from `src/instrumentation.node.ts`, which `register()` imports only when `NEXT_RUNTIME === "nodejs"` (the NodeSDK is not edge-compatible; the repo has no edge code). Vendor-neutral and configured by the standard `OTEL_*` variables. Rejected: `@vercel/otel` (swapping is a one-file change either way, so this door is cheap), gRPC.
- **Off without a destination:** the SDK starts only if `OTEL_EXPORTER_OTLP_ENDPOINT` is set (per-signal endpoint variables are not supported in the first cut). Otherwise nothing starts, `@opentelemetry/api` calls are no-ops, and there is no connection-refused noise (the NodeSDK default is `localhost:4318`).
- **Never blocking:** batch processors only (never `SimpleSpanProcessor`); exporter errors go to the OTel diagnostic logger, not to the request.
- **Depth (first cut):** framework spans only, no database spans. The metrics pipeline is wired; no custom metrics, no runtime-metrics instrumentation.
- **Variables:** `OTEL_EXPORTER_OTLP_ENDPOINT` (optional URL), `OTEL_EXPORTER_OTLP_PROTOCOL` (optional, `http/protobuf` or `http/json`), `OTEL_SERVICE_NAME` (optional, default `nextjs-starter`) are declared and Zod-validated in `env.server.ts`, so a typo is reported at startup by name (on Next.js 16.4.6 the process stays up and answers 500, see "Review of step 2"). The SDK reads the rest of `OTEL_*` itself; this is the documented exception to C11. `OTEL_EXPORTER_OTLP_HEADERS` may carry credentials in cloud: read only by the SDK, never logged, a commented line with a warning in `.env.example`.
- **Logger:** `src/lib/logger.ts` (`import "server-only"`), no dependency. API `logger.debug|info|warn|error(event, fields?)` and `logger.exception(event, err, fields?)`. Fields are typed `string | number | boolean | null` (no objects, no `Error`), strings truncated to 200 characters, and a runtime key deny-list (`/email|token|password|secret|authorization|cookie|body|dsn|url|key/i`) replaces values with `"[redacted]"`. `exception` records only `error_name`, `error_code` and `digest`, never message or stack. The methods return `Promise<void>` (Next 16 `headers()` is async); the promise never rejects, so callers may ignore it, and only code that must be sure the line was written awaits it (the wrapper and the hook do). The `headers()` call is wrapped in try/catch, which also swallows Next's dynamic-usage signal: acceptable because the logger is called only from dynamic code (actions, route handlers, the hook; the root layout already forces dynamic rendering with `connection()`). Do not call the logger from code that can be prerendered or from `"use cache"` scopes. `createLogger(options)` (sink, clock, request id source) is the test seam and `pickRequestId(headers)` the pure reader. Output is one JSON line `{ts, level, event, trace_id?, span_id?, request_id?, ...fields}` on stdout and also an OTel log record through the logs API (no-op without the SDK; in the api 1.10 line it is exported by `@opentelemetry/api` itself, and the separate `@opentelemetry/api-logs` package is not needed, see "Spike outcome"). `trace_id` comes from the active span; `request_id` is read from `x-request-id` or `x-vercel-id` through a guarded `headers()` call when present, absent outside a request, and never generated. Emission is wrapped in try/catch: a failing sink never affects the request (PH-AC-72). No log-level variable. ESLint `no-console` on `src/**` with the logger file exempt enforces use.
- **`onRequestError`:** logs only `context.routePath`, `context.routeType`, `request.method`, the error class name, `digest` and the database error code. Never `request.path` (query string may carry tokens or emails), headers, cookies or the message. The hook also logs `request_id` (read from the `x-request-id`/`x-vercel-id` entries of the `request.headers` argument only, via `pickRequestId`, never other headers). It builds a per-call logger with `createLogger({ readRequestId: () => pickRequestId(request.headers) })` instead of the default `headers()` reader, because `headers()` is not readable from the hook for route handlers (PH-T-63). The hook is observe-only; it cannot change a response. Raw error output printed by Next before the hook runs is a documented limit (ADR 0015, Consequences).
- **Local collector:** Grafana LGTM, one container, UI on host port 3001, all ports bound to `127.0.0.1`, image pinned to an exact tag, no volume, in `docker/observability/`, `pnpm obs:start` / `pnpm obs:stop`. Not part of `pnpm dev`, tests or CI. Rejected: Jaeger.
- **Test seams:** OpenTelemetry is tested with an in-memory exporter and a small OTLP receiver, never the collector.

## Consequences
- Positive: zero cost and zero failure modes when no endpoint is set; a cloud backend (Grafana Cloud, Sentry via OTLP) is `OTEL_*` variables only; logs and traces correlate.
- Negative: one new direct runtime dependency (`@opentelemetry/sdk-node`, exact-pinned, with a large transitive tree, subject to the 24-hour release-age gate of ADR 0010) plus one devDependency for the test helper (the first estimate of about 9 was reduced by the SDK-driven configuration, see "Implementation notes"); the own logger must be kept small.
- Updates convention C8 (the "no observability tooling" sentence is removed).
- **Spikes (first tasks):** `sdk-node` bundling and versions under Turbopack and Node 26 (may need `serverExternalPackages`); that a throwaway OTLP receiver gets a trace; `onRequestError` does not fire for `redirect()` and `notFound()`.
- **Peer range (settled by the PH-T-23 spike, see "Spike outcome"):** the recommendation written here before the spike (pin `@opentelemetry/api` to 1.9.x) was based on the wrong assumption and is superseded: the current SDK line requires api 1.10. `@opentelemetry/api` stays at 1.10.0 and the test helper's `@opentelemetry/sdk-trace-base` 2.12.1 is replaced by `@opentelemetry/sdk-trace` 3.1.1.
- Revisit: database spans or custom metrics when a feature needs them; `@vercel/otel` if the SDK proves fragile on Vercel.

## Spike outcome (PH-T-23, 2026-11-13)

Method: a scratch copy of the repo (outside the working tree; no throwaway code is committed) with a scratch `src/instrumentation.node.ts` imported from `register()` when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. It started `NodeSDK` with OTLP/HTTP trace, log and metric exporters, `BatchSpanProcessor`, `BatchLogRecordProcessor` and a `PeriodicExportingMetricReader`, then ran `pnpm build`, `next start -p <port>` and a plain Node `http` receiver on 127.0.0.1, with `curl` against `/api/health`. Node 26.13.1, Next 16.4.6, pnpm 12.18.0.

**Result: the approach works; one ADR assumption (the api 1.9.x recommendation) is replaced.**

- **Peer range: the recommendation was backwards.** npm registry state on 2026-11-13: there are two incompatible SDK generations. The current one (`sdk-node` 0.300 and 0.301, `sdk-logs`, `sdk-metrics`, `resources`, `core` and `sdk-trace` 3.x, all exporters 0.301.x) declares the peer `@opentelemetry/api` `>=1.10.0 <1.11.0` (exporters `^1.10.0`). The older one (`sdk-node` 0.223.x with `sdk-trace-base` 2.12.x, `core` and `resources` 2.12.x) declares `>=1.3.0 <1.10.0`. No 1.9.x satisfies the new line, and the old line cannot be combined with api 1.10. Decision: stay on the new line and `@opentelemetry/api` 1.10.0 (already pinned). The one package left on the old line is the devDependency `@opentelemetry/sdk-trace-base` 2.12.1, which is the only source of the `pnpm peers check` warning. Replace it with `@opentelemetry/sdk-trace` 3.1.1 (the 3.x name of the same package; `sdk-trace-base` has no stable 3.x). With the swap, `pnpm peers check` reports "No peer dependency issues found". `peerDependencyRules.allowedVersions` is not needed and must not be added.
- **Test helper impact:** `tests/utils/otel-test-tracer.ts` needs two edits for the 3.x API (verified in the scratch copy, typecheck and all 399 unit tests green): import from `@opentelemetry/sdk-trace`, `BasicTracerProvider` is now `TracerProvider`, and `new SimpleSpanProcessor(exporter)` is now `new SimpleSpanProcessor({ exporter })`. The logger itself uses only `trace.getActiveSpan` and `isSpanContextValid` and is unchanged. PH-T-25 does the swap in `package.json`, the lockfile and that helper (the tests must stay green).
- **Packages and exact versions to pin (all published 2026-11-12 17:09 UTC or earlier, so older than the 24-hour gate on 2026-11-13 22:39 UTC; `pnpm add` with `minimumReleaseAge: 1440` accepted them):** `@opentelemetry/sdk-node` 0.301.2, `@opentelemetry/exporter-trace-otlp-http` 0.301.2, `@opentelemetry/exporter-logs-otlp-http` 0.301.2, `@opentelemetry/exporter-metrics-otlp-http` 0.301.2, `@opentelemetry/sdk-logs` 3.1.1, `@opentelemetry/sdk-metrics` 3.1.1, `@opentelemetry/sdk-trace` 3.1.1 (`BatchSpanProcessor`), plus the existing `@opentelemetry/api` 1.10.0. `@opentelemetry/api-logs` is not needed: in this line the logs API is exported by `@opentelemetry/api` and `sdk-node` uses it. That is 8 direct packages (7 new), fewer than the "about 9" estimated above. `sdk-trace` is a direct dependency in the app and a devDependency only if the app does not import it; PH-T-25 chooses by what it imports. Re-check the registry and the gate when T-25 runs (versions move quickly: 0.301.1 and 0.301.2 are three days apart).
- **`pnpm` build-script gate:** `sdk-node` pulls `protobufjs` 7.6.6 through its gRPC exporters (not used here). `pnpm add` then fails with `ERR_PNPM_IGNORED_BUILDS`. PH-T-25 must add `protobufjs: false` under `allowBuilds` in `pnpm-workspace.yaml` (its install script is optional), with the same kind of comment as `esbuild`.
- **Bundling: no `serverExternalPackages` and no config change needed.** Both `next build` (Turbopack, the default) and `next build --webpack` compiled without warnings. In both cases `next start` loaded the SDK from `register()`, and the receiver got `POST /v1/traces` (Next framework spans) and `POST /v1/logs` (a record emitted through the logs API after `sdk.start()`). No metrics request was sent in the 12 s window: with no instruments there is nothing to export, which is the intended "pipeline wired, no custom metrics".
- **Off by default verified:** with the variable unset the server printed only the normal Next lines (the scratch import never ran, no "SDK started" line, no connection errors). With the endpoint pointing at a closed port (`127.0.0.1:4998`) three requests to `/api/health` returned 200 in 2 to 34 ms and nothing extra was printed (the OTel diagnostic logger is off by default).
- **Node 26:** no warnings or errors on Node 26.13.1 in build or start (`sdk-node` declares `engines.node >=22.15.0`).
- **Protocol caveat for PH-T-24 and PH-T-25:** the `exporter-*-otlp-http` packages send JSON (`content-type: application/json` observed); `http/protobuf` is the separate `exporter-*-otlp-proto` packages (same version, already installed as dependencies of `sdk-node`, so no extra pin is needed to import them). The declared variable `OTEL_EXPORTER_OTLP_PROTOCOL` (`http/protobuf` or `http/json`) therefore has to select the exporter class. PH-T-25 decides how (explicit selection, or letting `sdk-node` configure itself from the environment); the spike did not test the protobuf exporters. The endpoint given to the explicit `-http` exporter classes is the full signal URL, so a base `OTEL_EXPORTER_OTLP_ENDPOINT` needs `/v1/traces` and `/v1/logs` appended by the code, unlike the env-driven setup, which appends them itself.
- **Commands:** `npm view @opentelemetry/<pkg> time peerDependencies dependencies --json`; `pnpm add <pkg>@<exact>` and `pnpm remove`; `pnpm peers check`; `pnpm typecheck`; `pnpm vitest run --project unit`; `pnpm build`; `pnpm exec next build --webpack`; `next start -p <port>` with and without `OTEL_EXPORTER_OTLP_ENDPOINT`; `curl` on `/api/health`.

## Implementation notes (PH-T-25)

- **Protocol choice:** `src/instrumentation.node.ts` constructs `new NodeSDK({ serviceName })` and lets the SDK configure exporters from the `OTEL_*` variables. `OTEL_EXPORTER_OTLP_PROTOCOL` therefore selects the exporter class itself (`http/protobuf` is the SDK default, `http/json` selects the JSON exporter) and the base endpoint gets its signal paths appended by the SDK. Verified against a throwaway receiver: protobuf (`application/x-protobuf`) and JSON (`application/json`) both arrive at `/v1/traces` with the configured service name.
- **Dependencies, fewer than the spike list:** because the SDK builds the exporters and processors itself, the app imports only `@opentelemetry/sdk-node` 0.301.2 (dependency). The exporter, `sdk-logs` and `sdk-metrics` packages stay transitive and are not pinned directly. `@opentelemetry/sdk-trace` 3.1.1 is a devDependency for the test helper only. `pnpm peers check` reports no issues. Add direct pins later only if code imports them (for example `sdk-logs` in T-26).

## Review of step 2 (PH-T-31, 2026-11-13)

Architect check of the step 2 code and tests against this ADR. Decisions and corrections:

- **Deviation: exporters are not pinned in code.** The Decision text lists explicit OTLP/HTTP trace, log and metric exporters. The implementation (`new NodeSDK({ serviceName })`) lets the SDK build exporters, batch processors and the periodic metric reader from `OTEL_*`. Accepted because it keeps `OTEL_EXPORTER_OTLP_PROTOCOL` and the wire format in agreement by construction, appends the signal paths itself, and needs one direct dependency instead of eight. Still OTLP over HTTP with batch processors (never `SimpleSpanProcessor`), so "never blocking" holds. Cost: behavior is defined by the SDK's environment contract, not by our code (see the next point). Reversible in one file.
- **Consequence of SDK-driven config: more `OTEL_*` variables are honored than we declare.** The gate is only `OTEL_EXPORTER_OTLP_ENDPOINT`; once it is set the SDK also honors, for example, per-signal endpoints and protocols (`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, `..._PROTOCOL`), `OTEL_TRACES_EXPORTER`, `OTEL_SDK_DISABLED`, `OTEL_LOG_LEVEL`, batch tuning (`OTEL_BSP_*`, used by the E2E setup) and `OTEL_EXPORTER_OTLP_HEADERS`. The earlier statement "per-signal endpoint variables are not supported in the first cut" therefore means "not validated or documented", not "ignored". A per-signal `grpc` protocol would pass our validation (only the base variable is validated) and be honored by the SDK; it is unsupported. This is the documented C11 exception and is accepted for the first cut.
- **Startup failure is relaxed on Next.js 16.4.6.** A throwing `register()` (invalid `OTEL_*` value or any env error) does not exit the process: `next start` prints the error naming the variable (never the value), keeps running and answers every request with 500 (found by PH-T-28; spec PH-FR-13 and PH-AC-23 relaxed on 2026-11-13; proven by `tests/e2e/telemetry-config-startup.spec.ts`). This is the same behavior as the epic 001 variables (ADR 0004 amendment, architecture "Environment"). Forcing `process.exit(1)` was rejected: fragile on serverless platforms. The operational signal is the 500 health check plus the error line, so deployment checks must not rely on a crash.
- **Secrets.** `OTEL_EXPORTER_OTLP_HEADERS` is deliberately not declared in `env.server.ts`; no file under `src/` reads it, and the logger and `onRequestError` never see it. The OTel log record carries the same sanitized entry as the stdout line (typed primitives, key deny-list, truncation, errors reduced to name/code/digest), built once before both emissions. Residual risk: the SDK's own diagnostic logger (`OTEL_LOG_LEVEL`, off by default) can print exporter errors to the console; do not set it in production with credentials in the endpoint URL (an endpoint URL with embedded credentials is also discouraged: use the headers variable).
- **Network exposure.** The collector is bound to `127.0.0.1` (Decision above). `next start` itself listens on all interfaces by default (Next.js default hostname); that is a deployment concern shared with the whole app (the platform or a reverse proxy fronts it), not specific to telemetry, and no change is made. Local developers who do not want the dev or E2E server reachable on the LAN can pass `--hostname 127.0.0.1`.
- **Known limit: no flush on exit.** The SDK is not shut down on SIGTERM, so up to one batch interval of spans and logs can be lost when the process stops. Acceptable for the first cut; the seam is `startTelemetry()` returning the SDK (or registering `sdk.shutdown()` on `SIGTERM`) when a feature needs it.
- **Consistency checks passed:** SDK module imported only in the Node runtime and only when the endpoint is set (`register()`), so telemetry off costs nothing and prints nothing; `@opentelemetry/sdk-node` 0.301.2 and `@opentelemetry/api` 1.10.0 exact-pinned, `@opentelemetry/sdk-trace` 3.1.1 exact-pinned devDependency for the test helper only; the logger and `onRequestError` match the Decision text (including per-call request id source and no `request.path`); E2E harness strips inherited `OTEL_*` variables so a developer's shell cannot change test outcomes.
