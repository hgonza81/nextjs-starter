# Architecture

Short overview; decisions and reasons are in the ADRs ([index](adr/README.md)).

## Stack
Next.js (App Router, strict TypeScript), Supabase Auth, PostgreSQL with RLS, Drizzle ORM (`postgres` driver), Supabase CLI + Docker for local development and CI, Vercel deployment from GitHub Actions.

## Layout
```
src/
  app/              routing only; calls module public APIs
  modules/<name>/   index.ts (public API), actions/, queries/, schemas/, components/, types.ts
  db/               client.ts (private, lazy getDb()), rls.ts (withRls, withAnonymousRls), schema/ (generated), index.ts
  lib/              env.ts (public), env.server.ts (server-only), supabase/ (Auth clients only), utils; domain-free
supabase/           config.toml, migrations/ (SQL, source of truth), seed.sql
```
Modules `auth`, `users`, `tenants` arrive in epic 002.

## Dependency direction
`app` -> module `index.ts` -> `@/db`, `@/lib`. `lib` imports neither `modules` nor `db`; `db` imports nothing from `modules`; `app` and components never import `@/db`; no cycles. Enforced by lint in CI (ADR 0001).

## Data and security rules
- All table access goes through `withRls(ctx, fn)` (or `withAnonymousRls`); the raw DB client is private to `src/db`. The app connects as `app_backend`, which fails closed (ADR 0003). Never nest `withRls` calls (single connection: deadlock), never use session-level SQL state, never build SQL from request input.
- Every table needs explicit `GRANT`s and RLS policies in its own migration (default privileges for `anon`/`authenticated` are revoked); an `INSERT ... RETURNING` also needs a SELECT policy. The schema guard test queries the catalog, not the generated TS schema (which carries no RLS flag or grants).
- Data API (PostgREST, GraphQL) is disabled; Storage and Realtime are not used for app tables.
- `supabase-js` is for Auth only; no `.from()`/`.rpc()`. Data API disabled.
- Migrations are SQL-first in `supabase/migrations`; the Drizzle schema is generated by `pnpm db:schema` (wrapper over `drizzle-kit pull`) and drift-checked in CI: `supabase db reset`, `pnpm db:schema`, `git diff --exit-code src/db` (ADR 0002). Supabase CLI 3.1.0 (pinned), local Postgres 17.
- Tenant isolation: shared schema + `tenant_id` + RLS (ADR 0005).
- Environment access only through `src/lib/env.ts` (public) and `src/lib/env.server.ts` (server-only), validated at startup by `src/instrumentation.ts`; `next.config.ts` imports the public env so a build fails on missing `NEXT_PUBLIC_*` variables, which are therefore also needed by `next start` (ADR 0004).

## Conventions
kebab-case files; named exports; `@/` alias; Server Components by default; mutations via Server Actions returning `{ ok: true, data } | { ok: false, error }`; Zod validation at every boundary; structured server error logging without PII or secrets; Conventional Commits (documented, not enforced).

## Deployment
GitHub Actions runs fast checks and DB/E2E checks on every push; the deploy job (`vercel pull/build/deploy --prebuilt --prod`) `needs` all blocking jobs. Vercel Git auto-deploy is disabled. The deployed app has no database until a cloud project exists; `/api/health` is liveness only, DB checks run locally and in CI (ADR 0004).
