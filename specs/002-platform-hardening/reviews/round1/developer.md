# Review by developer — 002-platform-hardening — round 1 (requirements + flows; no wireframes yet)

## Summary
Feasible as written and proportionate for an MVP. Verified against the installed docs (Next.js 16.4.6, Node 26.13.1): `onRequestError`, `error.tsx` / `global-error.tsx` / `not-found.tsx`, `serverActions.bodySizeLimit`, `poweredByHeader` and nonce CSP via `proxy.ts` all exist. The biggest issue is Q6 and PH-AC-08: the framework digest is a weaker "reference code" than the flows assume (details below). The second is that a nonce-based CSP (Q2 A) makes every page dynamically rendered.

## Concerns and gaps
- [important] **Digest as reference code (Q6, PH-FL-01/04, BR-02, PH-AC-08).** `error.digest` is only set for errors thrown in Server Components. An error thrown in a Client Component has no digest and never reaches `onRequestError` (it happens in the browser), so "exactly one server log entry contains code X" cannot hold for those. Server actions and route handlers have no error page, so they need our own code anyway (the wrapper generates one; PH-FL-05 already says so). The digest is also a hash of the message and stack, so the same bug gives the same code for every user (acceptable; arguably useful; BR-02's "non-guessable" wording does not apply and should be dropped). Also `onRequestError` receives a React-processed error, so the digest must be read from `err.digest`, not computed.
- [important] **Nonce CSP forces dynamic rendering of every page (Q2 A, PH-HR-07).** Per the CSP guide, nonces only work with dynamic rendering and need `src/proxy.ts` (this Next.js version uses `proxy`, not `middleware`). Today `/` and `/design` are presumably static; they become per-request rendered, with no CDN-cacheable HTML. Fine for a SaaS behind login, but it is a real trade-off to record in the ADR. Dev needs `'unsafe-eval'`. Proxy also needs a matcher excluding `_next/static`, images and prefetches. `style-src` is the likely friction (Tailwind is a static stylesheet so fine; Radix/shadcn and `sonner` inject inline `style` attributes, which a nonce does not cover): expect `style-src-attr 'unsafe-inline'` or equivalent. That is the "relax the minimum" case Q2 already anticipates; PH-AC-31 (E2E, no violations) is the right proof.
- [important] **OpenTelemetry env vars vs ADR 0004 / C11.** The OTel SDK reads `OTEL_*` itself from `process.env`, while C11 forbids `process.env` outside the env modules and PH-FL-07 wants invalid values to fail at startup naming the variable. Needs: the `OTEL_*` variables declared (optional, Zod-validated) in `env.server.ts`, and the SDK still reading its own copy. Small, but a documented exception, not a surprise. The existing single-`NEXT_RUNTIME` lint exception in `instrumentation.ts` stays.
- [important] **OTel logs signal is the least stable part.** In the JS SDK, traces and metrics are stable; the logs SDK (`@opentelemetry/sdk-logs`, `api-logs`) is still on `0.x` versions with churn. Exporting logs via OTLP is therefore the highest-maintenance piece. Exact versions must be checked at implementation time (pinned, per ADR 0010); I did not verify the current `0.x` compatibility matrix here.
- [minor] **`@vercel/otel` vs raw `NodeSDK`.** The Next.js guide documents both. `@vercel/otel` is shorter and handles the edge runtime, but it wraps the SDK (extra layer, its own version pinning against `@opentelemetry/*` peers) and is Vercel-branded for a starter that is cloud-agnostic. Raw `NodeSDK` in `src/instrumentation.node.ts` (imported only when `NEXT_RUNTIME === 'nodejs'`, same pattern as today's `register()`) is ~30 lines, supports OTLP/HTTP for all three signals, and respects `OTEL_*` env vars natively. The app has no edge code, so the edge benefit is unused.
- [minor] **Auto-instrumentations are out.** `@opentelemetry/auto-instrumentations-node` is heavy and has ESM/bundling problems with Next (and Drizzle/postgres.js are not covered well). Next.js already emits spans for requests, rendering and route handlers. The epic should say "framework spans only"; DB spans can be a later add.
- [minor] **Request id.** Not provided by Next. Needs to be generated (in `proxy.ts`, set as request header and response header) or taken from `x-request-id`. `onRequestError` gets `request.headers`, so it can read it; the logger outside a request context simply omits it. Trace id comes from `trace.getActiveSpan()` in `@opentelemetry/api` (no-op when no SDK, which satisfies BR-09). Note `proxy.ts` is also needed for CSP, so one file covers both.
- [minor] **Logger design.** No dependency needed: a ~40-line module writing one JSON line to stdout. pino/winston are heavy and pino needs `serverExternalPackages` handling in Next. For BR-04 prefer an **allow-list by type** (fields limited to string/number/boolean ids and codes; errors passed as `{ name, code }` only) with a key deny-list (email, token, password, body, authorization, url with credentials) as a backstop; a deny-list alone cannot guarantee PH-AC-18. The OTel logs bridge is then an optional second sink of the same call, not a separate API.
- [minor] **Local collector port clash.** The Grafana LGTM image (`grafana/otel-lgtm`) serves its UI on 3000, the same as `next dev`; map it to another host port (for example 3001) and OTLP on 4317/4318. Put the compose file in `docker/` or `compose.observability.yaml` with `pnpm obs:up` / `pnpm obs:down` scripts. Image tag must be pinned (ADR 0010). Disk and RAM cost is notable (one fat container); stays optional (BR-11).
- [minor] **Telemetry unreachable (PH-AC-22).** The OTLP exporters retry and drop silently by default and the batch processors are async, so requests are not blocked. Use batch processors (not `SimpleSpanProcessor`, which the doc example uses and which exports synchronously). With no endpoint set, simply do not start the SDK (BR-09); the SDK would otherwise default to `localhost:4318` and log connection errors.
- [minor] **Next.js API differences to remember.** In this version the error boundary prop is `retry` (stable since 16.3; `reset` still exists but re-renders without refetching): use `retry` for "Try again". `global-error.tsx` must render its own `<html>`/`<body>` and does not get global styles or the theme, so it needs self-contained styling (as flows say). `error.tsx` and `global-error.tsx` are Client Components, so they cannot call the server logger; capture relies on `onRequestError` only.
- [minor] **Typed errors (PH-HR-03) and Next control flow.** `notFound()`, `redirect()` and `forbidden()` work by throwing special errors. The wrapper must rethrow them and never convert them to `unexpected`. This is easy to miss, and needs a test. Likewise `onRequestError` does not fire for these.
- [minor] **DB error mapping.** postgres.js errors carry a Postgres `code` (`23505` unique, `42501` insufficient privilege / RLS). Drizzle wraps some errors in `DrizzleQueryError` with the original in `cause`, so the mapper must inspect `cause` as well. Not found is not a DB error (zero rows); it is a handler decision.
- [minor] **Conventions check (PH-HR-08 / PH-AC-35).** An enforced check is a DB test (vitest `db` project) querying `information_schema` for tables in `public` lacking `created_at`/`updated_at`/trigger, with an explicit exceptions list. Feasible; no new tool. There are no tables yet (only role migrations exist), so the test needs a fixture table to prove it fails. The reusable trigger function (`set_updated_at`) must be `SECURITY INVOKER` with fixed `search_path`.
- [minor] **Pagination helper and `src/db` boundary.** The helper must run inside the caller's `withRls` and accept a Drizzle table/columns allow-list. Where it lives matters for lint rules: modules may import `@/db`, `src/lib` may not. So it belongs in `src/db` (exported through `@/db`), not `src/lib`. Action wrapper and error types are domain-free and belong in `src/lib` (but must not import `@/db`; the DB error mapper takes a plain `unknown`, so it is fine).
- [minor] **Generator.** `pnpm gen:module` is a small `scripts/gen-module.mts` (same style as `scripts/db-schema.mts`, Node 26 runs TS natively; no template library). Folder layout in C1 says "create only folders that have content", so "agreed structure" must be decided: recommend `index.ts` and `types.ts` only, no empty folders (this also answers Q7 consistently). Boundary lint needs no change (rule (a) is pattern-based), but PH-AC-50 should be tested with a fixture. The architecture doc says modules have `queries/`, the system prompt convention says `data/`: pick `queries/` (C1).
- [minor] **`X-Powered-By` and CORS.** `poweredByHeader: false` and no CORS headers (Next sends none by default, so "closed" means "nothing to add" plus a test). Server Actions already check Origin against Host; `bodySizeLimit` default is 1 MB, so the requirement is to set an explicit documented value (recommend keep `1mb`, explicit in config).
- [minor] **HSTS in dev/E2E.** Send HSTS only for production builds (the browser ignores it on http, but E2E over `next start` on localhost is http). Tests assert headers against `next start`, as flows say.
- [minor] **Existing code to touch.** `src/app/api/health/db/route.ts` (its C8 pattern logs `error.name`; becomes a logger call, and PH-AC-19 needs a lint rule `no-console` for `src` with the logger file as the exception, cheaper than a grep test). `src/instrumentation.ts` gains `onRequestError` and the SDK import. `docs/architecture.md` C8 says "No observability tooling in the MVP" and C1 says modules arrive in "epic 002": both need updating.

## Proposals
- Use raw `NodeSDK` + OTLP/HTTP exporters (traces, metrics, logs) in `src/instrumentation.node.ts`, started only when an OTLP endpoint is configured; no `@vercel/otel`, no auto-instrumentations. ADR for the telemetry approach (already required by PH-AC-56).
- Own logger in `src/lib/logger.ts` (no dependency), allow-list typed fields, trace id from `@opentelemetry/api`, request id from a `proxy.ts` header. `no-console` lint rule enforces PH-AC-19.
- `src/proxy.ts`: request id + nonce CSP (production) and the other security headers; static headers (HSTS, nosniff, referrer, permissions, frame-ancestors) can alternatively live in `next.config.ts` `headers()`, which keeps them working on static assets. Recommend all in `next.config.ts` except the CSP (nonce) in `proxy.ts`. Note `frame-ancestors` is part of the CSP; `X-Frame-Options: DENY` can be added as a legacy duplicate.
- Error codes: use the digest for page errors (Q6 A) and a generated short id for actions and route handlers; call it the same name in the UI ("reference").
- Defer test-file generation (Q7 A), the shared error renderer (Q8 A, delete PH-AC-48), and offset pagination with a stable secondary sort on `id` (Q5 A, needed for PH-AC-38 "stable for equal values").
- Suggested task order: error types and wrapper, logger, error pages plus `onRequestError`, OTel, headers/CSP, DB conventions, pagination, generator, collector and docs.

## Risks and assumptions
- Assumes Q3 A (hard delete, `created_at`/`updated_at` only) and the architect proposes the id type (recommend `uuid` via `gen_random_uuid()`, compatible with `auth.users.id`).
- OTel package versions with Node 26 were not verified here (no packages installed); the OTel SDK declares support for current Node LTS lines but Node 26 is new. Mitigation: verify with a spike as the first step of the OTel task; the SDK stays off when unconfigured, so a failure cannot break the app.
- Nonce CSP depends on Next internals injecting nonces into its own scripts; verified by PH-AC-31/32 in a real browser, which is the only reliable proof.
- Dev overlay and `'unsafe-eval'` in dev mean CSP and error-page behavior (PH-AC-06) must be tested against `next build && next start`, not `next dev`.
- Flows contain no wireframes yet; the three error screens are simple enough that an ASCII sketch in the designer's review (per specs/README.md) is enough.
